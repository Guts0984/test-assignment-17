# Тестовое задание: бронирование номеров для сети отелей

Система для небольшой сети отелей: гости бронируют номера на сайте, бронирования также приходят из внешнего канала продаж (OTA). Ревеню-менеджер управляет ценами и ограничениями. Ресепшн заселяет и выселяет гостей, назначает номера и ведёт счёт гостя. Горничные убирают номера. Каждую ночь в каждом отеле проходит ночной аудит: закрываются сутки, отмечаются незаезды, начисляется проживание. Канал продаж получает актуальные цены и наличие.

Если что-то неоднозначно — решите сами и запишите решение в README. История коммитов — по этапам работы, CI на каждый коммит.

## Сценарии

### Гость (сайт, без регистрации)

1. Выбирает отель, даты заезда и выезда, число гостей. Видит доступные типы номеров с ценой за весь период и разбивкой по ночам.
2. Начинает бронирование: номер **удерживается на 10 минут**, пока гость заполняет имя, email и телефон. На экране — обратный отсчёт.
3. Подтверждает бронирование и получает письмо с номером брони и ссылкой на управление ею.
4. По ссылке видит бронь, может изменить даты или число гостей и отменить. Перед отменой видит, будет ли штраф и какой.

### Ревеню-менеджер

1. Ставит цены по типу номера на диапазон дат («с 1 по 20 июня — 3 200», «выходные — +15 %»).
2. Ставит ограничения на даты: минимальный срок проживания, запрет заезда, запрет выезда, закрытие продаж.
3. Задаёт допустимый овербукинг по типу номера (по умолчанию 0).
4. Видит шахматку на 60 дней: по каждому типу и ночи — продано, свободно, цена, ограничения. Изменения других пользователей видны вживую.

### Ресепшн

1. Видит заезды, выезды и проживающих на сегодня по гостиничной дате отеля.
2. Назначает номер брони заранее или при заселении. Заселяет гостя только в чистый или проверенный номер.
3. Переносит гостя в другой номер, продлевает проживание, оформляет ранний выезд.
4. Ведёт счёт гостя: проживание, мини-бар, прочие услуги, оплаты, возвраты. Выселяет, только когда баланс счёта нулевой.
5. Разбирает овербукинг: бронь, на которую не хватило номеров, переселяет в номер выше классом или в другой отель сети.

### Горничная и старшая горничная

1. Горничная видит свои номера на сегодня с приоритетом: сначала номера под сегодняшний заезд.
2. Отмечает «убрано»; старшая горничная проверяет и ставит «проверено».
3. Старшая горничная распределяет номера между горничными и выводит номер из продажи (ремонт) на период с причиной.

### Администратор сети

1. Создаёт отели (часовой пояс, валюта, время заезда и выезда, время ночного аудита, правила отмены), типы номеров и номера.
2. Подключает канал продаж: адрес, ключ, какие отели и типы номеров в нём продаются.
3. Управляет сотрудниками и их ролями в отелях; видит упавшие фоновые задачи и запускает их повторно.

## Правила

| Что | Правило |
| --- | --- |
| Ночь | бронь занимает **ночи**: с даты заезда до даты выезда, не включая её. Даты — локальные даты отеля |
| Наличие | по каждому типу номера и ночи: продано + удержано ≤ номеров этого типа − номера на ремонте + допустимый овербукинг |
| Бронь на несколько ночей | все ночи бронируются вместе или ни одна |
| Удержание | 10 минут; истёкшее удержание возвращает номера в продажу ровно один раз; подтверждение в момент истечения — либо бронь, либо «удержание истекло», не оба |
| Цена | сумма цен по ночам; при подтверждении цена фиксируется и потом не меняется, если ревеню-менеджер поменял тариф |
| Ограничения | минимальный срок проверяется по ночи заезда; запрет заезда и запрет выезда — по соответствующим датам; закрытие продаж — по любой ночи брони |
| Отмена | бесплатно до 14:00 по времени отеля за 2 календарных дня до заезда; позже — штраф в размере первой ночи; правило по умолчанию, отель может задать своё |
| Незаезд | гость не заселился до ночного аудита после даты заезда — бронь `no_show`, начисляется штраф первой ночи, остальные ночи освобождаются |
| Изменение брони | новые даты проверяются и занимаются в одной транзакции; если не получилось — остаётся старая бронь без изменений. Цена новых ночей — по текущему тарифу, уже оплаченных — прежняя |
| Номер | один физический номер — не больше одного проживания в одну ночь; заселение — только в «чистый» или «проверенный»; после выезда номер «грязный» и попадает в уборку |
| Ночной аудит | раз в сутки в заданное время по местному времени отеля: незаезды, начисление ночи всем проживающим, закрытие гостиничной даты. Каждая гостиничная дата закрывается ровно один раз и по порядку; переход на летнее время учитывается |
| Овербукинг | бронь из канала на уже проданную ночь (канал ещё не получил обновление) **принимается**, помечается «овербукинг» и появляется у ресепшна; при заселении система предлагает бесплатный апгрейд в свободный номер выше классом |
| Канал продаж | бронирования из канала идемпотентны по номеру брони канала; у изменений и отмен из канала есть версия — устаревшая версия отбрасывается, а изменение, пришедшее раньше самой брони, не теряется |
| Цены и наличие в канал | подписаны HMAC; повторы с паузой; изменения по одному типу номера отправляются не чаще раза в 3 секунды, в последнем значении; у каждого сообщения растущая версия |
| Деньги | в минорных единицах валюты отеля (UAH, PLN, EUR); баланс счёта всегда равен сумме его строк; строки счёта не удаляются и не меняются — только сторно |

Статусы брони: `held`, `confirmed`, `checked_in`, `checked_out`, `cancelled`, `no_show`, `expired`. Таблица переходов (кто и из какого статуса) — в README.

Статусы номера: `clean`, `dirty`, `inspected`, `out_of_order`, плюс признак «занят».

**Журнал наличия:** каждое изменение занятости по ночам (удержание, бронь, отмена, изменение, незаезд, ранний выезд, продление, ремонт) — отдельная запись: тип номера, ночь, на сколько, по какому документу, кто, когда. Счётчики «продано» и «удержано» по каждой ночи всегда равны сумме журнала.

**Сид:**
- 3 отеля в трёх часовых поясах (`Europe/Kyiv`, `Europe/Warsaw`, `Europe/Lisbon`) и трёх валютах; заезд с 14:00, выезд до 12:00, ночной аудит в 03:00 по местному времени (в Киеве на переходе времени этого часа в одну ночь нет, а в другую он повторяется);
- по 5 типов и 150 номеров на отель;
- цены и ограничения на 2 года вперёд;
- 300 000 броней за 2 года, из них часть пришла из канала;
- 1 000 000 строк счетов;
- около 60 заездов, 60 выездов и 250 проживающих на сегодня в каждом отеле, несколько броней с овербукингом, несколько номеров на ремонте.

Логины — в README.

## Заглушка канала продаж

Отдельный сервис в `docker compose`:

- присылает бронирования, изменения и отмены: кнопкой на странице (одна или пачка из N) и по HTTP — им пользуются тесты;
- принимает цены и наличие, проверяет подпись и показывает на странице текущее наличие по типам и ночам с версиями;
- в режиме хаоса (переключатель в `.env`):
  - бронь отправляется дважды, одновременно в обе копии `api`;
  - отмена или изменение иногда приходят раньше самой брони;
  - каждое пятое входящее обновление цен и наличия получает ответ 500 или таймаут.

## Инварианты

Это главное, что проверяется. Каждый инвариант должен держаться при одновременных запросах, повторах, рестарте процессов и потере Redis, и на каждый нужен тест.

1. **Наличие не уходит в минус и не теряется.** Ни по одному типу номера ни в одну ночь продано + удержано не больше допустимого (кроме принятого овербукинга из канала); счётчики всегда равны сумме журнала.
2. **Последние номера продаются честно.** 200 одновременных бронирований на 5 последних номеров через обе копии `api`, с сайта и из канала, — подтверждено ровно 5 с сайта; брони из канала сверх наличия помечены овербукингом, ни одна не потеряна.
3. **Бронь на несколько ночей атомарна.** Две брони «1–5 июня» и «4–8 июня» на последний номер одновременно — одна получает все ночи, вторая ни одной.
4. **Удержание истекает один раз.** Подтверждение, пришедшее в момент истечения удержания, — либо бронь подтверждена, либо удержание истекло и номер вернулся в продажу; никогда оба и никогда ни одного.
5. **Номер не заселяется дважды.** Два администратора одновременно назначают один номер разным броням на пересекающиеся ночи — проходит одно назначение.
6. **Отмена не конфликтует с ночным аудитом.** Отмена, пришедшая в момент обработки незаезда, — либо отменена со штрафом по правилу, либо `no_show`; штраф начислен один раз.
7. **Ночной аудит — ровно один раз.** Каждая гостиничная дата каждого отеля закрывается один раз и по порядку: при нескольких копиях `worker`, `kill -9` посреди аудита, потере Redis и после простоя в несколько суток (каждые пропущенные сутки — по одному разу, по порядку).
8. **Импорт из канала идемпотентный.** Одна бронь, присланная 10 раз одновременно в обе копии `api`, — одна бронь, одно занятие ночей. Отмена, пришедшая раньше брони, — в итоге бронь отменена.
9. **Канал видит актуальное наличие.** При ошибках канала каждое обновление доходит после повторов; версии не идут назад; канал не видит наличие, которого уже нет дольше 3 секунд плюс время повторов.
10. **Фоновые задачи надёжны:**
    - `kill -9` воркера посреди ночного аудита или истечения удержаний — после рестарта всё доделано, двойных начислений нет;
    - несколько копий `worker` не выполняют одну задачу дважды;
    - задача, исчерпавшая попытки, видна администратору и запускается повторно вручную.
11. **Потеря Redis ничего не ломает.** После `FLUSHALL` удержания истекают, ночной аудит проходит, обновления в канал уходят, и ничего не выполняется дважды.
12. **Права — на сервере, в каждом эндпоинте и в сокетах:**
    - гость видит только свою бронь по ссылке, ссылку нельзя подобрать;
    - сотрудник видит только свои отели;
    - горничная видит только свои номера;
    - канал продаж видит только подключённые отели и типы номеров;
    - на некорректный ввод — понятная ошибка с кодом, одинаковая по формату во всех эндпоинтах и описанная в OpenAPI; никогда «Internal server error».

Время в задачах (10 минут удержания, дедлайн отмены, ночной аудит, 3 секунды канала) подменяется в тестах.

## Что сдать

- Репозиторий: `apps/api`, `apps/worker`, `apps/web`, `packages/shared`.
- Запуск: `cp .env.example .env && docker compose up --build`.
  - `docker compose`: `postgres`, `redis`, `api` ×2, `nginx`, `worker`, `web`, заглушка канала.
  - Миграции и сид создаются сами, других ручных шагов нет.
- Swagger на `/docs`; сгенерированный клиент совпадает со схемой — проверка в CI.
- Экран горничной работает с телефона (ширина 375 px), одной рукой: крупные кнопки, без таблиц.
- Шахматка ревеню-менеджера, экран ресепшна и наличие в заглушке канала обновляются вживую; обратный отсчёт удержания и «сегодня» отеля считаются по часам сервера.
- Формы с ошибками у полей.
- Поиск свободных номеров на 7 ночей по отелю — быстрее 200 мс; шахматка на 60 дней — быстрее 300 мс; поиск брони по номеру, фамилии, email — быстрее 300 мс; отчёт за 90 дней — быстрее 1 с.
- Отчёт для ревеню-менеджера: загрузка, средняя цена ночи, выручка на доступный номер, отмены и незаезды по каналам. Период и фильтры — в URL.
- e2e:
  - гость находит номер → удержание → подтверждение → письмо → канал видит уменьшенное наличие;
  - ресепшн назначает номер → заселение → начисление ночи на ночном аудите → оплата → выселение → номер в уборке → горничная убрала → старшая проверила → номер снова доступен для заселения;
  - бронь из канала на проданную ночь → овербукинг у ресепшна → апгрейд при заселении;
  - отмена после дедлайна → штраф в счёте; бронь без заезда → перевод часов через ночной аудит → `no_show` со штрафом.
- README:
  - запуск и тесты;
  - как устроено наличие по ночам и почему нельзя продать лишнее;
  - как защищены удержание, назначение номера, изменение и отмена брони от одновременных действий;
  - как считаются гостиничная дата, дедлайн отмены и время ночного аудита, с примером на переходе на летнее время;
  - список фоновых задач: когда ставятся, повторы, защита от дублей, восстановление после потери Redis;
  - как идёт обмен с каналом продаж в обе стороны и почему канал не видит устаревшее наличие;
  - таблицы статусов брони и номера;
  - индексы и ограничения в базе;
  - принятые решения.
